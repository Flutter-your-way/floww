## Feature Notes

- The "Meet WAVE" intro and "Three Modes" onboarding-intro screens are merged into a single view (`lib/core/auth/views/meet_waves_view.dart`). Tapping "Get Started" plays a custom staggered scale + fade transition (`lib/core/auth/widgets/step_reveal_item.dart`) between the two steps instead of navigating to a second route; the header back arrow reverses it. The old `welcomeToFlowView` route and `WelcomeToFlowView` screen were removed since nothing else referenced them.
- Added an "Account Setup" screen (`lib/core/auth/views/auth_view.dart`, route `AppRouter.accountSetup`) between the mode showcase and onboarding. "Skip for Now" still just proceeds to onboarding as a guest. Google and Apple (iOS only, via `Platform.isIOS`) sign-in are now real: `AuthService` (`lib/core/auth/services/auth_service.dart`) signs in through `firebase_auth` (Google via `google_sign_in` v7's `GoogleSignIn.instance`/`.authenticate()`, Apple via `sign_in_with_apple` with a SHA-256-hashed nonce), then reads/creates a `users/{uid}` Cloud Firestore doc to tell new vs. existing users apart and persist the `UserModel`. `AuthViewModel` (`lib/core/auth/view_models/auth_view_model.dart`) exposes per-provider loading flags and an error message, driving `CustomButton`/`CustomOutlinedButton`'s built-in loading/disabled state; a failure shows inline error text above the buttons. On success, the view routes via `AppRouter.routeAfterAuth(user)` — onboarding questions, Connect Wearables, or Home depending on `UserModel.onboardingCompleted`/`answersSubmitted` (see below) — using a new `NavigationService.pushAndRemoveUntil` (clears the back stack). `SplashView` now checks for an existing session the same way before deciding where to land. Notification permission (`FirebaseMessaging.instance.requestPermission`) is requested once `AuthView` loads, and the FCM token is registered into the user's Firestore doc after a successful sign-in. `CustomButton`/`CustomOutlinedButton` gained optional `leading`/`foregroundColor` params to support this screen's icon buttons.
- Built the Home screen (`lib/core/home/views/home_view.dart`, `HomeProvider` in `core/home/providers/`, section widgets in `core/home/widgets/`): Flow Score, Today's Habit, Today's Workout, Nutrition Summary, Apple Health Sync, Today's Progress, and Muscle Recovery cards, plus a conditional "How to Increase Your Flow Score" card (shown only at 0% flow score) and a Wave Insight banner (shown only when present). Ships with populated sample data by default, but every card's empty-state branch is driven by real (currently zero/empty) values, not dead code.
- Added `MuscleRecoveryCard` (`lib/core/home/widgets/muscle_recovery_card.dart`), shown below Today's Progress: front/back anatomical diagrams (`AppImages.muscleFront`/`muscleBack`, rendered as-is via `SvgPicture` — the highlighted-muscle coloring is baked into the SVGs themselves, not applied at runtime) plus a 2×2 stat grid (days since last workout, in recovery, ready muscles, fatigued muscles). Fixed `AppImages.muscleFront`/`muscleBack`, which previously pointed at `assets/icons/` (a non-existent path for these files) — added `AppImages._imagesBase` and repointed them at `assets/images/`, where the files actually live.
- Added the app shell (`lib/navigation/views/main_tab_view.dart`): a floating bottom tab bar over a `PageTransitionSwitcher` of 5 tabs (Home, Nutrition, Activity, Plans, Stats). Tab switches use a 300ms `FadeThroughTransition` from the `animations` package, filled with `context.colors.backgroundPrimary`; because only the selected tab is mounted, tab screens do not keep state across switches (state that must survive belongs in a provider). `AppBottomNavBar` (`lib/navigation/widgets/app_bottom_nav_bar.dart`) renders the 5 tabs as a pill with a circular selection indicator that slides between tabs via `AnimatedAlign`, plus a per-icon color crossfade. `WaveOrbButton` (`lib/navigation/widgets/wave_orb_button.dart`) is a press-animated stub for the floating WAVE AI orb — `onTap` is currently a no-op placeholder; wiring it to a real voice/AI screen is a follow-up. Nutrition/Activity/Plans/Stats currently render a shared `FeaturePlaceholderView` (`lib/config/widgets/placeholders/feature_placeholder_view.dart`) with a "Coming soon" message until those features are built. `AppRouter.home` now routes to `MainTabView` instead of `HomeView` directly.
- Onboarding now actually submits: `OnboardingDetailsEntity` (`lib/config/entities/onboarding_details_entity.dart`, previously unused) is built from the answers map and written to a new `onboarding_details/{uid}` Cloud Firestore collection (`AppCollection.onboardingDetails`) by the new `OnboardingService` (`lib/core/onboarding/services/onboarding_service.dart`), branching into exactly one of the gym/calisthenics/yoga detail blocks based on the selected training type. `OnboardingProvider.nextQuestion` is now async: completing the last question (`summary_screen`) submits the answers, sets `UserModel.answersSubmitted = true`, and — on success — `OnboardingQuestionView` navigates to a new `ConnectWearablesView` (`lib/core/onboarding/views/connect_wearables_view.dart`, route `AppRouter.connectWearables`). "Connect wearables" was removed from the question data entirely (was `apple_health` in `phase_5`) so it's a genuine final step outside the questionnaire; `HealthIntegrationWidget` was decoupled from `OnboardingProvider` (now takes `isConnected`/`onToggle`) so it's reusable standalone there. Finishing that screen sets `UserModel.onboardingCompleted = true` and goes to Home. `AppRouter.routeAfterAuth(user)` is the single place `SplashView`/`AuthView` use to decide between onboarding questions, Connect Wearables, and Home based on those two flags — so closing the app between submission and finishing the wearables step resumes exactly there instead of replaying the questionnaire.
- Added `HapticManager` (`lib/config/utils/haptics/haptic_manager.dart`), a static wrapper around the `haptic_feedback` package. Call `HapticManager.success()/.warning()/.error()/.light()/.medium()/.heavy()/.rigid()/.soft()/.selection()` from anywhere — each checks (and caches) `Haptics.canVibrate()` first and no-ops silently on unsupported platforms/devices. Not yet wired into any interaction; hook it into buttons/taps as needed.
- Apple Health is now a real integration, not a toggle. New feature module `lib/core/health/`: `HealthService` (`services/health_service.dart`) wraps the `health` package (HealthKit on iOS, Health Connect on Android) and owns the read-only type list (steps, active energy, heart rate, resting heart rate, sleep, workouts), permission requests, and a `fetchTodaySnapshot()` that returns a `HealthSnapshot` (`models/health_snapshot.dart`) with today's steps, active kcal, resting HR, sleep minutes and workout count; `HealthProvider` (`providers/health_provider.dart`) holds the `HealthConnectionStatus` (disconnected/connecting/connected/unavailable), the snapshot, sync + error state, and persists the connected flag to `SharedPreferences` under `health_connected`, restoring and re-syncing at app start. It is registered app-wide in `main.dart`. `HealthIntegrationWidget` now takes `isConnected`/`isConnecting`/`statusLabel`/`onConnect` — tapping the Apple Health row triggers the real system permission sheet, the pill shows a spinner while connecting and "Connected" after, and the synced summary (e.g. "8,432 steps · 7h 12m sleep") renders under the title. `ConnectWearablesView` writes the real granted state through `markWearablesStepDone`, and the Home screen's `AppleHealthSyncCard` is wired to the same provider (`connected`/`syncDetail`/`onConnect`/`onDisconnect`), replacing the removed `HomeProvider.healthSyncConnected` mock. Native setup: iOS gets `NSHealthShareUsageDescription`/`NSHealthUpdateUsageDescription` in `Info.plist` plus a new `ios/Runner/Runner.entitlements` (HealthKit capability, wired into all three Runner build configs); Android gets the Health Connect `<queries>`, rationale intent-filter, `ViewPermissionUsageActivity` alias, the six read permissions + `ACTIVITY_RECOGNITION`, and `minSdk = 26` (Health Connect's floor). HealthKit only returns data on a physical device — the iOS Simulator has no Health app. `AppRadius.xl4` (32) and `AppSizes.s120` were added so the widget's app-icon tile uses tokens instead of inline values.
- `AppBackground` (`lib/config/utils/backgrounds/app_background.dart`) gained a `scrollable` flag. When set, it owns the `SingleChildScrollView` itself and translates the background layer up with the scroll offset, so the background scrolls with the content instead of staying fixed; the shift is clamped at 0, so iOS pull-down bounce keeps the background pinned rather than revealing a gap above it. Pass plain (non-scrolling) content as `child` in this mode. The Home screen uses it.
- AI food scan data layer (the capture screen is described below). Backend lives in the sibling repo `/Volumes/T7/code/floww_cloud` (Express on Cloud Functions v2, `POST /food/scan`) — it sends the photo to OpenAI with a strict JSON schema and returns a typed food model: name, description, serving size/weight, confidence, health score, per-ingredient macros, and full nutrition (12 macros plus `waterMl`, 14 vitamins, 11 minerals; units are in the field names — `G`/`Mg`/`Mcg`/`Ml`). The Dart mirror is `FoodModel` (`lib/core/nutrition/models/food_model.dart`), field-for-field identical to the backend's `foodModelSchema`, so the returned object is saved unchanged unless the user edits it first (see the result sheet below). `FoodScanService` (`lib/core/nutrition/services/food_scan_service.dart`) has `scanFood(imageBytes:, mimeType:, note:)` (posts base64 JSON with the Firebase ID token via `dart:io` `HttpClient` — no new package) (saving moved to `NutritionLogService.addFoodLog`, which writes to `users/{uid}/food_logs/{food.id}` under the new `AppCollection.foodLogs` — see the Nutrition feature note). Server errors map to `FoodScanException` with a typed `FoodScanErrorCode` (`notFood`, `quotaExceeded`, `aiUnavailable`, `network`, …). The API base URL is `AppApi.baseUrl` (`lib/config/constants/app_api.dart`), overridable with `--dart-define=API_BASE_URL=...` for the local emulator. `test/fixtures/food_model.json` is generated from the backend's own sanitizer and schema; `test/food_model_test.dart` checks the Dart model round-trips it exactly — regenerate the fixture whenever the backend model changes. Firestore rules live in the backend repo at `floww_cloud/firestore.rules` (deploy with `firebase deploy --only firestore:rules`); they let each user read/write their own `users/{uid}`, `users/{uid}/food_logs` and `onboarding_details/{uid}`, and keep `ai_usage` server-only. A rule on `users/{uid}` does not cover its subcollections, so `food_logs` needs its own block — without it saving a scan fails with `[cloud_firestore/permission-denied]`.
- Built the Nutrition tab (`lib/core/nutrition/views/nutrition_view.dart`) from the "date change / nothing logged" design: header with a working date selector (prev/next arrows, tap the date to open a date picker, range ±365 days), empty-state card, Daily Goal card (calories + segmented protein/carbs/fats bar), a tip card, a Weekly Nutrition Report card (Mon–Sun range of the selected date), and floating Scan / Log Food buttons above the tab bar (Scan opens the AI Food Scan screen; Log Food opens the Log Food sheet — see the full Nutrition feature note below). `NutritionViewModel` moved to `lib/core/nutrition/view_models/nutrition_view_model.dart` and owns all date logic and copy: title reads "Today's" for today and the weekday otherwise, and the empty-state/tip text switches between past, today and future dates. Goals come from `NutritionGoal.defaults` (2,450 kcal / 200g / 310g / 90g) until real targets are computed. Shared pieces extracted so Home and Nutrition use the same widgets: `HomeCard` became `AppCard` (`lib/config/widgets/cards/app_card.dart`, new `glow` variant), the two-line greeting/title became `ScreenTitle` (`lib/config/widgets/headers/screen_title.dart`, now used by `HomeHeader`), and the macro label became `MacroValueLabel` (`lib/config/widgets/nutrition/macro_value_label.dart`, now used by `NutritionSummaryCard`). New tokens: `AppTypography.heading3Medium` (20px, mapped to `textTheme.headlineSmall`), `AppGradientTokens.glowCard` (per mode) and `macroProtein`/`macroCarbs`/`macroFats`. New utils `AppDateUtils` (`lib/config/utils/dates/`) and `NumberFormatter` (`lib/config/utils/formatters/`). New icon `AppImages.foodScanIcon`.
- AI Food Scan screen (`lib/core/nutrition/views/food_scan_view.dart`, route `AppRouter.foodScan`, opened from the Nutrition Scan button). A live back-camera preview fills the whole screen (cover-cropped), with the "AI Food Scan" `CustomHeader`, the white corner-bracket scan frame (`FoodScanFrame`), a dark bottom scrim (new `AppGradientTokens.cameraScrim`), and a shutter button. Tapping the shutter takes the photo, freezes the preview on that frame, and hides the controls. While `FoodScanService.scanFood` runs, a line sweeps up and down across the frame: everything above the line is sharp and everything below is blurred (`FoodScanSweep`). When the scan succeeds, the screen pops and returns the `FoodModel` as the route result without saving it, and the Nutrition tab then opens the AI Food Scan result sheet (below). When it fails, the server's message is shown above the shutter and the live preview resumes so the user can retake. New `camera` package (approved): `FoodCameraService` (`services/food_camera_service.dart`) owns the `CameraController` at `ResolutionPreset.high` (~1280px JPEG, which matches the backend's downscale guidance) with audio disabled, and maps permission/startup/capture failures to `FoodCameraException`. `FoodScanViewModel` (`view_models/food_scan_view_model.dart`) owns the status (`starting`/`ready`/`capturing`/`scanning`/`suspended`/`unavailable`) and the app lifecycle. It releases the camera when the app goes inactive and restarts it on resume. A denied/unavailable camera is retried only after the app has really been in the background (e.g. the user went to Settings), so Android permission dialogs can't cause a retry loop. `NavigationService.pop` now takes an optional result. Native setup: iOS `NSCameraUsageDescription` in `Info.plist`; Android's `CAMERA` permission is merged from the plugin's manifest. The iOS Simulator has no camera, so it shows "No camera found on this device." — test capture on a physical device. Next to the shutter there is a photo-library button (`PhotoLibraryService`, `services/photo_library_service.dart`, new `image_picker` package) that picks a photo instead of taking one and then runs the same scan — this is what makes the flow testable on the Simulator, so it stays enabled (and centred) even when the camera is unavailable. The picker downscales to 1280px at JPEG quality 85, which re-encodes HEIC to the JPEG the backend expects. While a picked photo is being analyzed it replaces the camera background (`FoodScanViewModel.scannedPhoto`, cover-cropped under the scan frame and sweep), so you see what is being scanned; camera captures keep the frozen preview instead. Cancelling restarts the live preview; when there was no camera to begin with, the previous message comes back. It is a normal button in release builds too — gate it behind `kDebugMode` in `FoodScanView` if it should not ship. iOS needs `NSPhotoLibraryUsageDescription` (added); Android's system photo picker needs no permission. `test/food_scan_view_model_test.dart` covers capture/scan and library-pick success and failure plus the lifecycle rules with fake services.

Buttons: "Edit Meal" and "Start Workout". While saving, the sheet can't be dismissed. The close button discards the result; system back while editing returns to the review. **Water end-to-end:** the backend (`floww_cloud`) gained `macros.waterMl` in its schema and prompt (prompt version `food-scan-v2`), and `MacroNutrients.waterMl` reads a missing value as 0 so older logs still parse. New: `copyWith` on `FoodModel`/`FoodNutrition`/`MacroNutrients`/`Minerals` for the edited fields; micronutrient goals on `NutritionGoal` (fiber 30 g, sugar 50 g, sodium 2300 mg, water 2500 ml); tokens `AppColorTokens.scrim`, `borderAccent` (per mode, 50% accent), `proteinAccent`, `carbsAccent`, `fatAccent`. - Full Nutrition feature (first functional pass — UI polish comes later). **Data:** every food log is a `FoodLog` (`models/food_log.dart`) — the `FoodModel` JSON plus `mealType` (`breakfast`/`lunch`/`dinner`/`snacks`) and `loggedAt` (UTC ISO string); logs saved before this change fall back to `createdAt` and a time-of-day meal, but only documents with `loggedAt` match day queries. Water is a separate `users/{uid}/water_logs/{id}` collection (`WaterLog`, new `AppCollection.waterLogs`). `NutritionLogService` (`services/nutrition_log_service.dart`) owns all reads/writes: live `watchLogs(from, to)` (food + water combined, single-field `loggedAt` range, so no composite index), `watchRecentFoodLogs`, `fetchFoodLogs`, add/delete food and water. Every screen subscribes to the stream, so anything logged in a sheet appears everywhere instantly. `FoodScanService.saveFood` was removed in favour of it. **Domain:** `NutritionDay` (`models/nutrition_day.dart`) aggregates a day (calories, macros, fiber, sugar, sodium, water = drinks + water from food, per-meal totals, `DayLogStatus` full ≥3 meals / partial / none) and scores **Flow Points: 25 per day across 9 `FlowCategory`s** — Calories 5 and Carbs/Fats 3 (full within ±10% of goal, zero beyond ±50%), Protein 5 / Water 3 / Fiber 2 (progress to goal), Meal Timing 2 (1 per two meals logged), Sugar 1 / Sodium 1 (at or under the limit). Food categories need at least one food log; water counts on its own. The week max is 175, which is what the Nutrition card, the past-day impact card, the info sheet and the weekly report all read, so their numbers always agree. Goals stay `NutritionGoal.defaults` (2,450 kcal · 200g P · 310g C · 90g F · 30g fiber · 50g sugar · 2,300mg sodium · 2,500ml water) until per-user targets exist. **Nutrition tab** (`NutritionViewModel` rewritten around the day stream): today always shows the full layout — "Start Tracking Today" card when nothing is logged, otherwise the Diet Plan card — plus Recent Food Logs (tap to re-log to the same meal, with an Undo snackbar), Calorie Summary ring, Macronutrients (tap → sheet), Water/Fiber/Sugar/Sodium tiles (Water → sheet), Meal Breakdown (tap a meal with items → Meal Details, empty meal or the bright "ADD MEAL" pill → Log Food), Nutrition Flow Points (ⓘ → info sheet), Weekly Nutrition Report. **Past days are read-only** (following the "Historical data (read-only)" design, so Flow Points can't be backfilled): they show the "How this day's nutrition contributed to your Flow Score" breakdown and the read-only pill, and hide Scan/Log Food, meal "+" buttons, deletes and water quick-add; empty past days keep the empty-state card. Future days allow pre-logging and keep the "Nothing logged yet" + Daily Goal + Plan Ahead layout until something is logged. **Sheets** (all on the shared floating sheet): Log Food (`views/log_food_sheet.dart`, `LogFoodViewModel`) searches a local 30-item `FoodCatalog` (`models/food_catalog.dart`, USDA-style values per serving, logged as `FoodSource.manual`), meal chips, and a per-row toggle — + logs the food into the selected meal, ✓ marks a food already in that meal and tapping it again unlogs it (`LogFoodViewModel.toggle`/`remove` deletes that meal's most recent matching log via `deleteFoodLog`, other meals untouched); Water Intake (`WaterIntakeViewModel`) with goal ring, Small/Glass/Bottle/Large quick add, custom ml (max 3,000), the day's log with swipe-to-delete and a "From meals" row; Macronutrients (`MacronutrientsViewModel`) with the day's calorie split, Protein/Carbohydrates/Fats tabs, grams vs goal, kcal/g, description, pro tips and recommended range (static copy on the `MacroNutrient` enum); Nutrition info (Flow Points explanation + Got it). **Screens** (shared `InnerPageScaffold`, `config/widgets/scaffolds/`): Meal Details (`AppRouter.mealDetails`, `MealDetailsArgs`) with meal header + macro split bar, Food Items (swipe to delete, Add Food Item → Log Food), a rule-based Nutrition Insight, and a Meal Timeline that switches meals in place; Weekly Nutrition Report (`AppRouter.weeklyNutritionReport`, Mon–Sun of the selected date) with FLOW Contribution + daily point bars, Consistency (days logged, calorie/protein streaks of consecutive days ≥70% of goal counted back from today, per-day full/partial/none dots), a Calories/Protein/Fiber bar chart with average over logged days and weekly total vs goal, the 9-category points breakdown, and a tip pointing at the biggest missed category; 30-Day WAVE Diet Plan (`AppRouter.dietPlan`): no AI backend yet, so `DietPlan.generate` (`models/diet_plan.dart`) deterministically builds 30 days × 4 meals from template meals scaled to the calorie goal. The start date is saved per user in `SharedPreferences` (`DietPlanService`) the first time the screen opens, and a day counts as completed when that date's logged calories reach 80% of the plan day. Days expand to show meals and daily totals. **Shared pieces added:** `AppProgressBar`, `AppProgressRing` (`config/widgets/progress/`), `AppChipTabs` (`config/widgets/tabs/`), `CardHeader` (`config/widgets/headers/card_header.dart` — `HomeCardHeader` moved here with optional `icon`/`trailing`, Home cards updated), optional `footer` on `AppSheetPanel`, optional `icon` on `NutritionTipCard`, `AppDateUtils.atTimeOf/shortWeekday/monthDayYear/time/relativeDay`, `Vitamins.zero`/`Minerals.zero`, and `FoodModel.copyWith(id:, createdAt:)`. **One macro palette everywhere:** protein lime `#C3FF3D` (`proteinAccent`), carbs orange `#F97316` (`carbsAccent`), fats cyan `#28D5E6` (`fatAccent`), fixed across all three visual modes — the `macroProtein/Carbs/Fats` gradients ramp from the same three accents. **Backend:** `floww_cloud/firestore.rules` gained a `users/{uid}/water_logs` owner-only block (redeploy with `firebase deploy --only firestore:rules`, otherwise water logging fails with permission-denied). **Stats always follow food:** `NutritionLogService.combineLogs` emits food as soon as it arrives and treats a failing water query (e.g. rules not deployed) as "no water" instead of blocking the whole day — previously a denied water query meant the day stream never emitted, so scanned meals saved but every stat stayed at 0. Unreadable log documents are skipped (`parseDocuments`) rather than breaking the stream, and `loggedAt` is written at fixed millisecond precision (`AppDateUtils.isoKey`) so day-range string queries compare correctly. **Day-wise:** every screen queries only the selected day, and `DayRolloverTimer` (`config/utils/dates/`) moves "today" to the new date at midnight — the Nutrition tab jumps forward if it was showing the day that just ended, and Home re-subscribes — so today's meals never carry into tomorrow's stats (only the Recent Food Logs quick-add row intentionally lists earlier foods). **Home tab:** `HomeProvider` now takes `NutritionLogService` and watches today's logs, so the Nutrition Summary card (calories, protein, carbs, fats), the Water Intake habit (drinks + water from food vs the 2.5 L goal) and Today's Progress (Habits count, Nutrition complete at ≥90% of the calorie goal) update live; the other Home cards are still sample data. **Not done yet:** the WAVE orb, Plans and edit-an-existing-log flows are untouched. **Tests:** `nutrition_day_test.dart` (totals, status, all 25 points, partial scoring, limits), `diet_plan_test.dart`, `weekly_report_view_model_test.dart`, `log_food_view_model_test.dart`, plus the scan-result tests ported to the new save path, all against `test/fakes/fake_nutrition_log_service.dart`.
- Smooth (iOS / Figma "corner smoothing") corners everywhere via the `smooth_corner` package. All rounded shapes go through `AppShapes` (`lib/config/theme/app_shapes.dart`, smoothness `0.6` — Figma's closest match to iOS): use `AppShapes.decoration(borderRadius:, color:, gradient:, image:, side:, shadows:)` instead of `BoxDecoration(borderRadius: ...)` (note `border: Border.all(...)` becomes `side: BorderSide(...)` and `boxShadow` becomes `shadows`), `AppShapes.border(...)` instead of `RoundedRectangleBorder`, `SmoothClipRRect(smoothness: AppShapes.smoothness, ...)` instead of `ClipRRect`, and the new `SmoothInputBorder` (`lib/config/widgets/text_field/smooth_input_border.dart`) instead of `OutlineInputBorder` for text fields. All 65 rounded decorations, 6 clips, 6 text-field borders and the date-picker sheet shape across auth, onboarding, home, nutrition, navigation and shared widgets were converted. Pills keep working because the radius is clamped to half the shortest side, and animated shapes (chip tabs) still lerp. True circles (`BoxShape.circle`) are unchanged — smoothing a circle is visually identical. Two behaviour notes: `ShapeDecoration` does not inset content by the border width the way `BoxDecoration` did (a 1–1.5px difference on bordered boxes), and it asserts that `color` and `gradient` are not both set — `FlowScoreCard` had both (the gradient fully covered the color), so its hidden `color` was removed.

  **Subscriptions are stored, not mocked — the payment itself is the only simulated part.** The plan catalog stays in code (`PremiumService.features`/`plans`, ₹499/month, ₹3,999/year), but the user's plan lives on the user's own document rather than in a parallel collection: `users/{uid}` carries `isPremium` and `planName` at the top level (the two fields anything outside the premium feature needs) and nests the rest under a single `subscription` map (`SubscriptionEntity.toUserFields()`/`toSection()`: `planId` (`floww_premium_monthly` / `floww_premium_yearly`), `status` active/cancelled, `term`, `price`, `currency`, `periodLabel`, `planName`, `startedAt`, `renewsOn`, `trialEndsOn`, `cancelledAt`, `isSimulated`, `updatedAt`), with one document per payment under `users/{uid}/invoices` (`SubscriptionInvoiceEntity`, which carries the same `planId`/`currency` so an invoice says which plan it paid for). The two plans are the single source of truth for those fields: `AppSubscription` (`config/constants/app_subscription.dart`) holds each plan's id, price, currency and billing length, and the `SubscriptionTermFields` extension derives `planId`, `price` and `periodEndFrom(start)` from a `SubscriptionTerm` so a plan can never be written with a mismatched id or renewal date. Documents saved before `planId` existed still read back — the term fills it in. `firestore.rules` enforces the same shape server-side: a write to `users/{uid}` that carries a `subscription` map only lands if its `planId` is one of the two, its price equals that plan's price, the currency is `INR`, the status/term are known values and the caller owns the document — every other user-document write (profile edits, FCM tokens, login stamps) is unaffected; invoices are create-only under the same plan/amount check and can never be updated or deleted. `PremiumService.watchSnapshot()` combines the user document and the invoice query into a `PremiumSnapshot`; `subscribe(term)` batch-writes the subscription fields (merged into the user document, so nothing else on it is touched) plus its invoice and stamps both `isSimulated: true` (no gateway is called and no card is charged — swapping in a real one means replacing this one method); `cancel()` updates only `subscription.status`/`cancelledAt`/`updatedAt` through dotted field paths and keeps `renewsOn` as the access-until date, so `isPremium` stays true for the rest of the paid period.

## Strict Coding Rules every time to follow

- Follow current coding style 
- Dont ever try to write comments in any conditions, so writing comments is strickly pohibited
- No hardcoded values until only screen specific or components specific and not available in config — colors, spacing, dimensions, font sizes, radii, etc. Always pull from `config/constants` or `config/themes`.
- Use EdgeInsets.symmetric instead of EdgeInsets.fromLTRB or others until its important at all places.
- No hardcoded images — any image asset a screen needs must first be added to `assets/images/` (or `assets/icons/` for icon assets), then declared as a named constant in `AppImages` (`lib/config/constants/app_images.dart`), and only then referenced from that constant in a View/widget. Never reference an asset path string directly in a View.
- No inline `TextStyle` — every text (only until its screen or component specific) widget uses the global text theme (`app_text_theme.dart`).
- Reuse before creating — check `config/widgets` and the feature's own `widgets/` folder before building something new.
- Shared widgets (buttons, text fields, cards, loaders, dialogs used across features) go in `config/widgets`; single-feature widgets go in `core/<feature>/widgets/`.
- No duplicate UI — if the same element appears in two or more places, extract it into a reusable widget.
- No UI built inline inside variables — extract non-trivial widget trees into proper widget classes.
- Never rebuild native system UI — no custom status bar, home indicator, or gesture area; that's the OS's responsibility.
- Strict MVVM — Views render UI only, ViewModels own logic and state, Services own data/IO. No business logic in Views.
- All features live under `core/<feature>/{services,view_models,views,widgets}`; new features follow this structure automatically.
- Pixel-perfect UI — the provided images of design is the source of truth for spacing, color, typography, sizing, alignment, shadows, and layout.
- Every color, gradient, and text style must be pulled from the app theme system (`Theme.of(context)` + custom `ThemeExtension`s). Never hardcode raw `Color(0x...)` / `LinearGradient(...)` values inside a screen, widget, or component. If a value isn't in the token set, add it to the token set — don't inline it.
- Extract design tokens (colors, spacing, typography, radius, dimensions, shadows) into constants/themes instead of hardcoding them in widgets.
- Keep code modular, readable, and small — prefer composition over duplication.
- Consistent naming across files, classes, methods, and widgets.
- Prefer `const` constructors/widgets wherever possible.

A transition lock stops two cinematics overlapping — `_settle` retries every 200ms while one is in flight — and `_begin` arms a 6s watchdog (`AppMotion.modeTransitionWatchdog`) that force-applies the target mode if the overlay is ever torn down without reporting completion, so the lock can't deadlock the system. `setAppActive` defers transitions while the app is backgrounded. In debug builds `debugForceTransition` plus a hidden long-press on the Flow Score card (`FlowModeDebugTrigger`) cycles the modes; it compiles out of release.
- The transition itself is a full-screen layer, not a dialog or sheet. `FlowModeTransitionHost` is mounted in `MaterialApp.builder` (`lib/main.dart`) so it renders above every route, and `FlowModeTransition` (`lib/core/flow_mode/widgets/flow_mode_transition.dart`) is the reusable component — it takes `mode`/`previousMode` and drives one `AnimationController` through timings in `AppMotion`: the veil blurs and darkens in over the first 12%, the mode visual builds, the title and message rise and scale in at 34–70%, the theme is applied at 62% via `applyTransitionTheme`, then the content clears at 72–86% and the veil dissolves at 82–100% so the copy is never left floating over live UI. Per-mode duration, easing and letter-spacing come from `AppModeIntensity`. Haptics are mode-specific (soft / selection / medium, with a second light tap at the Flow burst). It is wrapped in a transparent `Material` so the copy inherits a real text style, and in an `AbsorbPointer` so taps can't land mid-cinematic.
- The three modes share one visual system driven by a fragment shader rather than three hand-painted animations. `shaders/orb.frag` samples `assets/icons/restore_orb.png` for the sphere only — every texture read goes through `discToUv(..., uCoreR)` and the composite gates on `coreMask` — and generates the eight orbit rings and their travelling bubbles procedurally, so the lines actually revolve instead of the ring layer tumbling rigidly. The sampled artwork is reduced to luminance and remapped onto a four-stop palette (`AppOrbPalette`, `lib/config/theme/app_orb_palette.dart`) rather than hue-shifted, which keeps the ribbon shapes while giving each mode a clean colour. `AnimatedOrb` (`lib/config/widgets/effects/animated_orb.dart`) is the shared widget: it sizes itself to the texture's 1296:1214 aspect, because the shader's disc mapping only stays circular in texture space at that ratio and the measured `uCenter`/`uCoreR` would otherwise miss the painted sphere edge. `OrbShader` (`lib/config/utils/effects/orb_shader.dart`) preloads the program and a `ui.Image` in `main()` next to `LiquidGlassShader`, so the first transition never renders an empty centre, and falls back to a static image if the shader is unavailable. `ModeOrbVisual` picks the palette and per-mode motion (`orbSpin`, `orbOrbit`, `orbRingGlow` on `AppModeIntensity`) so Restore is slow and low-glow, Steady balanced, Flow fast and bright.
- The whole app carries the active mode, not just the transition. `AppModeIntensity` (`lib/config/theme/app_mode_intensity.dart`) is a third `ThemeExtension` alongside `AppColorTokens`/`AppGradientTokens`, read through `context.intensity`, holding motion scale, glow strength, ambient opacity/period/radius and the orb's motion per mode; because it is a `ThemeExtension` its values interpolate with the theme instead of snapping. `MaterialApp` now animates theme changes over `AppMotion.modeShift` with `modeRelease` easing, `FlowModeAmbientLayer` adds one cheap additive bloom pair drifting behind the tab shell at mode-specific speed and opacity, and the existing `AppBackground` crossfade continues to carry the per-mode artwork. Reduced motion (`MediaQuery.disableAnimationsOf`) shortens the transition to `AppMotion.modeTransitionReduced`, drops the blur, scale and travel, stops the orb's spin, orbit and ambient ticker, and renders a static frame — the mode change and its copy are preserved.

- Connected Apps & Devices is now interactive in both directions. Previously `ConnectedAppsViewModel.connect(id)` only ever set a source to connected and the row's `PillButton` was handed `onPressed: null` once `isConnected` was true, so every already-connected row rendered as a dead grey chip with no way back. `connect` became `setConnected(id, bool)`: it applies the change optimistically, awaits the write, and on failure restores the previous item and publishes an `errorMessage` that the view renders as an `AppErrorCard` above the list (its retry button dismisses). Disconnecting is confirmed first through the existing `AppConfirmSheet` — destructive styling, `Icons.link_off_rounded`, "Disconnect" against "Keep Connected" — matching how log out is confirmed on the Profile screen. In-flight rows are tracked in a `_pending` set so the button shows `PillButton.isLoading` and ignores taps, and the Firestore listener leaves pending ids on their optimistic value so a mid-write snapshot cannot flip the switch back under the user. This required `SettingsService._setFlag` to stop swallowing its outcome: it now returns `Future<bool>` (false when there is no signed-in preferences document or the write throws), and `setConnected`/`setNotificationEnabled` return that through, so a failed save is visible to the caller instead of silently reported as success.
