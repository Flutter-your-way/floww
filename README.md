## Feature Notes

- The workout share sheet's **Stories** button now hands the card straight to Instagram Stories instead of opening the generic share sheet. `InstagramStoriesService` (`config/utils/share/instagram_stories_service.dart`) calls the `floww/instagram_stories` method channel, which is implemented natively with no new packages: on iOS (`ios/Runner/AppDelegate.swift`) it puts the PNG on the pasteboard as `com.instagram.sharedSticker.stickerImage` and opens `instagram-stories://share` (`instagram-stories` is in `LSApplicationQueriesSchemes`); on Android (`InstagramStoriesChannel.kt`) it writes the PNG to cache, exposes it through `InstagramStoriesFileProvider` and fires `com.instagram.share.ADD_TO_STORY` (`com.instagram.android` is in `<queries>`). The card is sent as a sticker, so Instagram picks the background colours. If Instagram isn't installed, or the handoff fails, the button falls back to the system share sheet. Meta asks for a Facebook App ID as `source_application`; supply it with `--dart-define=FACEBOOK_APP_ID=<id>` (read by `AppSocial.facebookAppId`). Strava still uses the system share sheet.
- Settings now has an "Onboarding Answers" item (Profile → Settings, route `AppRouter.onboardingAnswers`). It lists every questionnaire answer grouped by onboarding phase, including the gym/calisthenics/yoga phase for the chosen training type. `OnboardingAnswersService` reads `onboarding_details/{uid}` and maps it back to the questionnaire answer keys. Tapping an answer opens `OnboardingAnswerEditView` (route `AppRouter.editOnboardingAnswer`), which reuses `OnboardingQuestionRenderer` on an `OnboardingProvider` seeded with the saved answers. If the edit leaves required questions unanswered (for example, switching training type), the editor walks through those questions before saving. Saving rebuilds the details with `OnboardingDetailsEntity.fromAnswers` and merges them into the document, keeping the blueprint and timestamps. The existing `onOnboardingDetailsWritten` trigger then recalculates nutrition targets. To support this, `OnboardingData.activePhasesFor` now holds the phase-branching logic and `OnboardingProvider.isAnswered` holds the per-question validation.
- Every user gets a personal, standard 30-day workout plan built from their onboarding answers. The new `generateWorkoutPlan` Cloud Function (`functions/src/handlers/workout.handler.ts` → `handleGenerateWorkoutPlan`) reads `onboarding_details/{uid}` and the user's seeded `workout_exercises` library, turns the answers into a `PlanProfile` (`helpers/workout.plan.profile.helper.ts`: training type, experience, chosen weekdays, session length, goal, split, equipment, injuries, calisthenics max reps, yoga style/meditation), filters the library to exercises the user can actually do (equipment, home-gym bar moves, calisthenics bar/dip requirements, injury exclusions), and builds a rules-based standard week (`helpers/workout.plan.template.helper.ts`: Full Body A/B/C, Upper/Lower, Push/Pull/Legs (5 days = PPL + Upper + Lower), Bro Split or Yoga flows; slots filled by movement pattern; sets/reps/rest/RIR by goal and experience; main-exercise count by session length). That week is sent to OpenAI (`prompts/workout.plan.prompt.ts`, structured output whose `exerciseId` is an enum of the allowed library ids, so the model can only pick real exercises); the answer is clamped and validated (`helpers/workout.plan.helper.ts`) and any day with fewer than 2 main exercises falls back to the standard day. If the AI is unavailable or over quota (`workoutPlan`, 5/day premium, 3/day free) the standard plan is used, so the endpoint always returns a plan. The program is always named "Your Workout Plan" (`WORKOUT_PLAN_NAME` on the backend, `WorkoutProgramEntity.generatedName` in the app; the AI only writes its description). Plans generated before the rename are renamed once by `WorkoutViewModel._renameGeneratedPlan`, which saves the program and reschedules upcoming sessions so their labels update and is saved as `workout_programs/wave-30-day-plan` (`lengthDays: 30`, `isGenerated: true`, `isCustom: true`) and `workout_state/state.generatedProgramId` is set. On the client, `WorkoutViewModel` calls it automatically once for every user who has no generated plan yet (`workout_state/state.generatedProgramId` unset), including existing users with a catalog program active, which the WAVE plan replaces. It then starts the plan through the normal `scheduleProgram` path, which keeps already-logged sessions; the Overview (when no program is active) and the Programs tab show a "Build / Rebuild my plan" card (`WorkoutPlanGeneratorService`, `WorkoutPlanBuilderItem`, reusing `WorkoutShiftCard`). Fixed-length programs carry `WorkoutProgramEntity.lengthDays` and `ActiveProgramEntry.totalDays` (`endDate` = start + 30 days, `dayNumberAt`, `weekAt` by day), are scheduled 30 days ahead, and follow the standard block in `ProgramPhase` (`core/workout/models/program_phase.dart`): week 1 Foundation (+1 rep in reserve), weeks 2–3 Build, week 4 Peak (+1 set on the first two main lifts), days 29–30 Deload. Plan labels read "Plan · Day 12 of 30 · Build", and the active-program card, program list, detail sheet and start sheet show days instead of weeks. The exercise library gained 21 calisthenics, dumbbell/home and yoga movements (catalog version 5) so bodyweight and yoga plans are complete.
- Missed workouts are now caught up *alongside* today's workout instead of shifting the whole program. "Do it today" (History tab, any missed program session in the last 7 days) and the "Missed X yesterday → Add to today" offer call `WorkoutPlanService.scheduleCatchUp`, which only sets `rescheduledTo: <today>` on the missed day's plan document; today's own plan is untouched. `watchCatchUps(date)` streams them. Sessions now record `planDate` when they fulfil another day's plan (`WorkoutSessionEntity.scheduledDate`/`isCatchUp`; `startSession(plan, on: today)`), so a catch-up counts toward today's Flow Score while `completeWorkout`/`unlogWorkout` link and unlink the *missed* day's plan (`planDayOf`). The history analyzer judges each day by sessions scheduled for it, so a made-up day turns green, and shows "Scheduled for today" while it is pending. The Overview shows a "Today's Plan" agenda card (`WorkoutAgendaCard`/`WorkoutAgendaRow`) whenever a day has two or more workouts: each row shows Scheduled/Catch-up, Ready/Up next/In progress/Completed, and a Start, Resume or View action; catch-ups can be removed with ×. The header shows "x of y done" plus 30-day plan progress. Viewing a completed row switches the stats below to that session. The FAB resumes whichever session is in progress, otherwise starts the next pending workout ("Start Catch-up" when it is a catch-up), and Today's Workout opens catch-ups through `TodaysWorkoutArgs(catchUpFrom:)`.
- Active workouts no longer run a wall-clock session timer. The clock pill was removed from the active-workout header (`CustomHeader` lost `isTimerMode`/`timeText`), the Workout-tab FAB now shows logged/planned sets instead of a ticking time, and the one-second rebuild tickers are gone (the active-workout ticker now only notifies while a rest countdown is changing). Duration is counted from the sets themselves: `WorkoutSessionEntity.activeSeconds` sorts every logged set by `loggedAt`, starts with the first set's work time (`LoggedSetEntry.workSeconds` — timed sets use their seconds, rep sets use `reps × secondsPerEffortRep`), then adds each gap between sets, never less than that set's work time and capped at 15 minutes so idle time is not counted. `trackedSeconds` uses that for in-progress sessions and the saved `durationSeconds` for completed ones. `timerResumedAt` was removed; pause/resume now only freezes the rest countdown.
- Workout start is instant. `TodaysWorkoutView` and the Workout-tab resume FAB pass an `ActiveWorkoutArgs` (`core/workout/models/active_workout_args.dart`) holding the plan, recent history and any in-progress session they have already loaded, so `ActiveWorkoutViewModel.load` skips its network fetches and shows the session on the first frame. `WorkoutSessionService.startSession` no longer waits for the server to confirm the new document (Firestore writes it locally first), `linkSession` runs in the background, and the unseeded path loads program state and history in parallel. Exercise images are preloaded: `RemoteImage` now builds one shared provider per URL for each of two sizes (thumbnail and full-width), and `ImagePrecacher` (`config/widgets/images/image_precacher.dart`) warms both for every exercise on the Workout tab, Today's Workout and the active workout, so the hero image appears with no loading flash. Images are loaded through `CachedNetworkImageProvider` (`cached_network_image`), so they are also saved to disk and show instantly after an app restart.

- AI food scan data layer (the capture screen is described below). Backend lives in the sibling repo `/Volumes/T7/code/floww_cloud` (Express on Cloud Functions v2, `POST /food/scan`) — it sends the photo to OpenAI with a strict JSON schema and returns a typed food model: name, description, serving size/weight, confidence, health score, per-ingredient macros, and full nutrition (12 macros plus `waterMl`, 14 vitamins, 11 minerals; units are in the field names — `G`/`Mg`/`Mcg`/`Ml`). The Dart mirror is `FoodModel` (`lib/core/nutrition/models/food_model.dart`), field-for-field identical to the backend's `foodModelSchema`, so the returned object is saved unchanged unless the user edits it first (see the result sheet below). `FoodScanService` (`lib/core/nutrition/services/food_scan_service.dart`) has `scanFood(imageBytes:, mimeType:, note:)` (posts base64 JSON with the Firebase ID token via `dart:io` `HttpClient` — no new package) (saving moved to `NutritionLogService.addFoodLog`, which writes to `users/{uid}/food_logs/{food.id}` under the new `AppCollection.foodLogs` — see the Nutrition feature note). Server errors map to `FoodScanException` with a typed `FoodScanErrorCode` (`notFood`, `quotaExceeded`, `aiUnavailable`, `network`, …). The API base URL is `AppApi.baseUrl` (`lib/config/constants/app_api.dart`), overridable with `--dart-define=API_BASE_URL=...` for the local emulator. `test/fixtures/food_model.json` is generated from the backend's own sanitizer and schema; `test/food_model_test.dart` checks the Dart model round-trips it exactly — regenerate the fixture whenever the backend model changes. Firestore rules live in the backend repo at `floww_cloud/firestore.rules` (deploy with `firebase deploy --only firestore:rules`); they let each user read/write their own `users/{uid}`, `users/{uid}/food_logs` and `onboarding_details/{uid}`, and keep `ai_usage` server-only. A rule on `users/{uid}` does not cover its subcollections, so `food_logs` needs its own block — without it saving a scan fails with `[cloud_firestore/permission-denied]`.

- AI Food Scan screen (`lib/core/nutrition/views/food_scan_view.dart`, route `AppRouter.foodScan`, opened from the Nutrition Scan button). A live back-camera preview fills the whole screen (cover-cropped), with the "AI Food Scan" `CustomHeader`, the white corner-bracket scan frame (`FoodScanFrame`), a dark bottom scrim (new `AppGradientTokens.cameraScrim`), and a shutter button. Tapping the shutter takes the photo, freezes the preview on that frame, and hides the controls. While `FoodScanService.scanFood` runs, a line sweeps up and down across the frame: everything above the line is sharp and everything below is blurred (`FoodScanSweep`). When the scan succeeds, the screen pops and returns the `FoodModel` as the route result without saving it, and the Nutrition tab then opens the AI Food Scan result sheet (below). When it fails, the server's message is shown above the shutter and the live preview resumes so the user can retake. New `camera` package (approved): `FoodCameraService` (`services/food_camera_service.dart`) owns the `CameraController` at `ResolutionPreset.high` (~1280px JPEG, which matches the backend's downscale guidance) with audio disabled, and maps permission/startup/capture failures to `FoodCameraException`. `FoodScanViewModel` (`view_models/food_scan_view_model.dart`) owns the status (`starting`/`ready`/`capturing`/`scanning`/`suspended`/`unavailable`) and the app lifecycle. Cancelling restarts the live preview; when there was no camera to begin with, the previous message comes back. - AI Food Scan result flow (`lib/core/nutrition/views/food_scan_result_sheet.dart`, `FoodScanResultSheet.show`, opened by the Nutrition tab once the scan returns a `FoodModel`). It is a floating sheet over a blurred, dimmed Nutrition screen: a new shared `showAppFloatingSheet` + `AppFloatingSheet` (`lib/config/widgets/sheets/app_floating_sheet.dart`; slide-up transition, keyboard-aware bottom inset, animated height between steps) plus `AppSheetPanel` (`app_sheet_panel.dart`; title + close button, subtitle, scrollable body, footer). **Review** step ("AI Food Scan"): `DetectedMealCard` shows the meal name with "(estimated)", total kcal and its share of the daily goal, Protein/Carbs/Fat tiles, and Fiber/Sugar/Sodium/Water bars against their daily goals (`MicronutrientProgressList`). Buttons: "Edit Meal" and "Start Workout". ## Strict Coding Rules every time to follow

- Follow current coding style 
- Dont ever try to write comments in any conditions, so writing comments is strickly pohibited
- No hardcoded values until only screen specific or components specific and not available in config — colors, spacing, dimensions, font sizes, radii, etc. Always pull from `config/constants` or `config/themes`.
- Use EdgeInsets.symmetric instead of EdgeInsets.fromLTRB or others until its important at all places.
- No hardcoded images — any image asset a screen needs must first be added to `assets/images/` (or `assets/icons/` for icon assets), then declared as a named constant in `AppImages` (`lib/config/constants/app_images.dart`), and only then referenced from that constant in a View/widget. Never reference an asset path string directly in a View.
- No inline `TextStyle` — every text (only until its screen or component specific) widget uses the global text theme (`app_text_theme.dart`).
- Reuse before creating — check `config/widgets` and the feature's own `widgets/` folder before building something new.
- Shared widgets (buttons, text fields, cards, loaders, dialogs used across features) go in `config/widgets`; single-feature widgets go in `core/<feature>/widgets/`.
- No duplicate UI — if the same element appears in two or more places, extract it into a reusable widget.
- No UI built inline inside variables — extract non-trivial widget trees into proper widget classes.
- Never rebuild native system UI — no custom status bar, home indicator, or gesture area; that's the OS's responsibility.
- Strict MVVM — Views render UI only, ViewModels own logic and state, Services own data/IO. No business logic in Views.
- All features live under `core/<feature>/{services,view_models,views,widgets}`; new features follow this structure automatically.
- Pixel-perfect UI — the provided images of design is the source of truth for spacing, color, typography, sizing, alignment, shadows, and layout.
- Every color, gradient, and text style must be pulled from the app theme system (`Theme.of(context)` + custom `ThemeExtension`s). Never hardcode raw `Color(0x...)` / `LinearGradient(...)` values inside a screen, widget, or component. If a value isn't in the token set, add it to the token set — don't inline it.
- Extract design tokens (colors, spacing, typography, radius, dimensions, shadows) into constants/themes instead of hardcoding them in widgets.
- Keep code modular, readable, and small — prefer composition over duplication.
- Consistent naming across files, classes, methods, and widgets.
- Prefer `const` constructors/widgets wherever possible.
- No new packages or architectural patterns without approval — reuse the existing stack and conventions.

The Express/Cloud Functions backend lives in the sibling `floww_cloud` repo; its `functions/` folder is mirrored into this repo at `functions/` and wired into the root `firebase.json`, so the function can be deployed from either side — keep the two copies in sync: the uid comes from the verified bearer token, so a caller can only delete themselves, and the Admin SDK has no recency rule. Common exercises (the gym, cable, machine and core moves plus the general bodyweight and dumbbell ones) show in every user's library as before. The pool (the ten yoga poses, Parallel Bar Dip, Inverted Row and Pike Push-Up) is marked `isPool: true` in `WorkoutCatalogData` and is still seeded into `users/{uid}/workout_exercises`, so the plan generator can choose from it, but `ExerciseCatalogEntry.isAvailable` keeps it out of the Exercise Library, the Add Exercise picker and the swap sheet until it is unlocked for that user. `WorkoutCatalogService.unlockInto` sets a per-user `isUnlocked` flag (kept out of `toCatalogJson`, so re-seeding never resets it) whenever a program is scheduled (`WorkoutPlanService._scheduleInto`) or a plan is saved (`savePlan`, which covers WAVE swaps), so a pool exercise appears only for users whose own workout uses it. A starred pool exercise stays visible, and the library also shows any pool exercise the user has already trained. Catalog version 6 re-seeds the pool flags and unlocks the exercises in each user's active and generated programs, so existing plans keep their exercises visible.
- The "Saving your workout" overlay was redesigned. The black disc, glowing spinner ring and generic dumbbell icon are gone. `WorkoutFinishOverlay` now shows the real workout being saved, left-aligned over the blurred session: a status line (a pulsing lime dot and "Saving", which becomes a check and "Saved"), the workout name in `heading1`, then Duration, Sets and Volume rows (Volume is hidden for bodyweight-only sessions) that slide in one after another while their numbers count up from zero, and a Flow Score row that pulses until the server responds and then shows `before → after` with the change in lime. A thin lime bar fills to 86% while saving and completes when the save lands. The data comes from `ActiveWorkoutViewModel.finishSummary` (`WorkoutFinishSummary`/`WorkoutFinishStat` in `active_workout_view_data.dart`), which replaces the old `finishLoadingTitle`/`finishDoneMessage` strings. Clock formatting moved to `NumberFormatter.clock`. Motion tokens: `workoutFinishPulse`, `workoutFinishRowStep`, `workoutFinishRowSpan`, `workoutFinishRowRise` and `workoutFinishLoadingFill` replace the spin and glow tokens.
- The Workouts tab's Overview now shows the day's planned workout to every user. The "Scheduled For Today" `SuggestedWorkoutCard` (workout name, duration, intensity, the plan reasons and a Start Workout button) was wrapped in the `personalizedRecommendations` premium gate, so free users saw only the locked "Personalized Recommendations" card, even though Home's `TodayWorkoutCard` shows the same plan ungated. The gate was removed, so the two screens now match. The card still shows only when the day has no logged session and fewer than two workouts (otherwise the agenda card takes over).
- Delete Account now shows that it is working. The backend wipe can take several seconds, and the only feedback was that the Danger Zone row stopped responding to taps. While `PrivacyDataViewModel.isDeleting` is true, `DangerZoneCard` (new `isLoading` flag) swaps its chevron for a red `AppSpinner`, and the subtitle changes to "Deleting your account…" until the request finishes.
- Logging out or deleting your account no longer plays a Flow Mode cinematic over the login screen. Signing out made the Home record streams fall back to empty data, so `HomeProvider` reported a new score while the session was ending, and `FlowModeController` animated a mode change (for example "FLOW MODE · You're in the zone.") on top of Account Setup. The new `FlowModeController.endSession()` cancels any pending settle or watchdog timer, drops any transition already in flight, and ignores `reportScore` until the next `resetSession()` (called when a new `HomeProvider` starts after sign-in). `ProfileView` and `PrivacyDataView` call it before signing out or deleting, and call `resetSession()` again if that fails, so a failed attempt leaves Home behaving normally.
